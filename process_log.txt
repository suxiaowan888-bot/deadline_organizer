Part 3: Check dates (dates.py)

Design decision: Python calculates dates, not the model. Language models
are often wrong at calendar math and may invent a date. The model only picks
out the date words; Python turns them into a real date or refuses.

parse_date() returns one of four statuses:
  ok       - one clear date -> the agent may save the task
  unclear  - vague, contradictory, or two possible dates -> ask the user
  missing  - no date at all -> ask the user
  past     - the date has already passed -> tell the user

Test: 11 example phrases with a fixed "now" (Sunday, 22 Nov 2026, 10:00),
so the results are the same on every run. All 11 matched the expected result.

  Friday afternoon    ok       Friday, 27 Nov 2026, 17:00  'afternoon' was read as 17:00.
  tomorrow at 3pm     ok       Monday, 23 Nov 2026, 15:00
  Nov 30 9am          ok       Monday, 30 Nov 2026, 09:00
  in 3 days           ok       Wednesday, 25 Nov 2026, 23:59  No time was given, so 23:59 (end of day) was used.
  next Friday         unclear  'next Friday' could mean either date.  Options: 27 Nov / 04 Dec
  sometime next week  unclear  'sometime' is too vague to pick one date.
  Submit the report   missing  No date was found.
  Sunday              unclear  Today is Sunday, so it could mean today or next week.
  Friday Dec 5        unclear  The phrase says Friday, but 05 Dec is a Saturday.
  Feb 30              unclear  That calendar date does not exist.
  today 8am           past     Sunday, 22 Nov 2026, 08:00  This date and time is already in the past.

Why "next Friday" is unclear: English speakers disagree on whether it means
this coming Friday or Friday of next week, so Python returns both options
and the agent asks the user to choose.

Part 4: Define the tools (tools.py)

The model gets a menu of three tools and chooses one:
  add_task(title, date_phrase) - save a task; Python checks the date words
  list_tasks(limit)            - show upcoming deadlines
  ask_user(question)           - ask when the date is missing or unclear

The model only proposes a tool. Nothing is saved yet. Python will check and
run each proposal in Part 5.

Part 5: Parser, validator, and executor (tools.py)

The model only proposes a tool call. Python decides whether it is allowed:
  Parser    (read_tool_call)     - reads the tool name and arguments
  Validator (validate_tool_call) - checks the rules before anything runs
  Executor  (run_tool)           - runs the tool, then re-reads tasks.json
                                   to confirm the task was really saved

Key rule: the validator checks that date_phrase appears in the user's own
words. "Never invent a date" is not only a prompt hint; Python enforces it.

  Part 6: The agent loop (agent.py)

Loop for each user message:
  model proposes a tool -> parser -> validator -> executor
  -> result goes back to the model as an observation -> repeat
The loop stops when the model replies with text, calls ask_user,
or reaches MAX_STEPS (6).

The program also has:
  - state: the messages list (the model remembers the conversation)
  - trace: every decision, tool call, and result, saved to trace.txt
  - budget: MAX_STEPS
  - evidence check: after each message, Python counts the tasks in
    tasks.json and warns if the model claims a save that did not happen
  - "file" command: prints tasks.json from disk without the model
